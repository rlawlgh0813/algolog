# AlgoLog 프로젝트 명세

## 1. 프로젝트 정의

AlgoLog는 알고리즘 문제 풀이를 구조적으로 기록하고, 풀이 과정에서 발생한 오답 원인과 반례를 함께 관리하는 학습 기록 서비스입니다.

이 프로젝트의 중심은 일반적인 게시글이 아니라 **풀이 기록(SolutionRecord)** 입니다. 사용자는 문제에 대한 풀이 메모, 접근 방식, 실수 포인트, 해결 상태, 복습 필요 여부, 공개 여부를 기록할 수 있으며, 실패했던 테스트케이스는 **반례(CounterExample)** 로 별도 관리합니다.

## 2. 문제의식

블로그나 노션에 알고리즘 풀이를 기록하면 자유롭게 작성할 수 있지만, 다음과 같은 한계가 있습니다.

- 문제 번호, 플랫폼, 난이도, 태그를 구조적으로 관리하기 어렵다.
- 어떤 반례에서 실패했는지 따로 찾기 어렵다.
- 오답 원인과 수정 과정을 일관된 형식으로 남기기 어렵다.
- 복습이 필요한 문제를 다시 찾기 어렵다.
- 특정 조건으로 풀이 기록을 검색하거나 필터링하기 불편하다.
- 같은 문제에 대한 다른 사람의 구조화된 풀이 기록을 탐색하기 어렵다.

AlgoLog는 이 한계를 해결하기 위해 문제 정보, 풀이 기록, 반례를 분리하여 저장합니다.

## 3. 핵심 가치

### 3.1 구조화된 문제 풀이 기록

문제의 플랫폼, 번호, 제목, 난이도를 별도 도메인으로 관리합니다. 이를 통해 같은 문제에 대한 여러 사용자의 풀이 기록을 연결할 수 있습니다.

### 3.2 오답 과정 중심의 기록

정답 풀이만 저장하는 것이 아니라, 막혔던 지점, 실수 포인트, 오답 원인, 해결 메모를 함께 기록합니다.

### 3.3 반례 중심 학습

실패한 입력, 기대 동작, 틀린 이유, 수정 메모를 CounterExample로 분리합니다. 반례는 풀이 기록의 부가 정보가 아니라 이 프로젝트의 차별점입니다.

### 3.4 복습과 탐색

해결 상태, 복습 필요 여부, 공개 여부를 통해 사용자가 자신의 학습 기록을 관리하고, 공개된 풀이를 탐색할 수 있게 합니다.

## 4. MVP 범위

### 4.1 인증

- 회원가입
- 로그인
- JWT 기반 인증

### 4.2 문제 관리

- 문제 등록
- 문제 단건 조회
- 문제 목록 조회
- 플랫폼, 난이도, 문제 번호 기반 검색 또는 필터

### 4.3 풀이 기록 관리

- 풀이 기록 작성
- 내 풀이 기록 목록 조회
- 풀이 기록 상세 조회
- 풀이 기록 수정
- 풀이 기록 삭제
- 해결 상태 관리
- 복습 필요 여부 관리
- 공개 / 비공개 설정

### 4.4 반례 관리

- 반례 작성
- 특정 풀이 기록에 연결된 반례 조회

### 4.5 탐색

- 공개 풀이 목록 조회
- 특정 문제의 공개 풀이 조회
- 플랫폼, 난이도, 해결 상태, 복습 필요 여부 기반 필터

## 5. MVP 제외 범위

이번 1차 구현에서는 아래 기능을 제외합니다.

- 댓글
- 좋아요
- 팔로우
- 소셜 로그인
- 코드 실행
- 자동 채점
- 실시간 알림
- 관리자 기능
- 복잡한 프론트엔드
- 커뮤니티 중심 기능

제외 이유는 프로젝트의 핵심이 커뮤니티가 아니라 **풀이 기록과 반례 관리 도메인 설계**이기 때문입니다.

## 6. 핵심 도메인

### 6.1 User

사용자 정보와 인증의 기준이 되는 도메인입니다.

예상 필드:

- id
- email
- password
- nickname
- createdAt
- updatedAt

### 6.2 Problem

알고리즘 문제 자체의 메타데이터를 관리합니다.

예상 필드:

- id
- platform
- problemNumber
- title
- difficulty
- createdAt
- updatedAt

설계 이유:

- 같은 문제에 대해 여러 사용자가 풀이 기록을 작성할 수 있습니다.
- 문제 정보를 풀이 기록마다 중복 저장하지 않고 별도 엔티티로 분리합니다.
- 플랫폼 + 문제 번호 조합에 유니크 제약을 둘 수 있습니다.

### 6.3 SolutionRecord

특정 사용자가 특정 문제에 대해 작성한 풀이 기록입니다. AlgoLog의 핵심 도메인입니다.

예상 필드:

- id
- author
- problem
- title
- solutionMemo
- mistakeNote
- solvingStatus
- reviewNeeded
- visibility
- createdAt
- updatedAt

설계 이유:

- 게시글이 아니라 학습 기록이라는 의미를 명확히 하기 위해 Post가 아닌 SolutionRecord라는 이름을 사용합니다.
- User와 Problem 사이의 기록을 표현합니다.
- 공개 여부와 작성자 정보를 통해 조회 권한을 판단합니다.

### 6.4 CounterExample

풀이 과정에서 실패했던 테스트케이스와 수정 과정을 기록합니다.

예상 필드:

- id
- solutionRecord
- inputExample
- expectedBehavior
- wrongReason
- fixMemo
- createdAt
- updatedAt

설계 이유:

- 반례는 풀이 기록의 단순 문자열 필드보다 별도 엔티티가 적합합니다.
- 하나의 풀이 기록에 여러 개의 반례가 연결될 수 있습니다.
- 오답 원인과 수정 메모를 구조화하여 복습 가치가 높아집니다.

## 7. 권한 정책

- 비공개 풀이 기록은 작성자만 조회할 수 있습니다.
- 공개 풀이 기록은 다른 사용자도 조회할 수 있습니다.
- 풀이 기록 수정과 삭제는 작성자만 가능합니다.
- 반례 작성은 해당 풀이 기록 작성자만 가능합니다.
- 반례 조회는 풀이 기록 조회 권한을 따릅니다.

## 8. 예외 처리 정책

필수 예외 상황:

- 존재하지 않는 사용자 조회
- 존재하지 않는 문제 조회
- 존재하지 않는 풀이 기록 조회
- 존재하지 않는 반례 조회
- 중복 이메일로 회원가입
- 권한 없는 비공개 풀이 조회
- 권한 없는 수정 / 삭제 요청
- Validation 실패

예외 응답은 프로젝트 전역에서 일관된 형식으로 처리합니다.

## 12. 포트폴리오 강조 포인트

- 단순 게시판이 아니라 알고리즘 학습 기록이라는 문제의식이 분명합니다.
- Problem, SolutionRecord, CounterExample을 분리하여 도메인 설계 의도를 보여줄 수 있습니다.
- 반례와 오답 원인을 별도 엔티티로 관리해 프로젝트 차별점을 만들 수 있습니다.
- 인증, 인가, CRUD, 검색, 예외 처리, Validation을 통해 백엔드 기본기를 보여줄 수 있습니다.
- README와 docs를 통해 설계 이유를 설명 가능한 형태로 남깁니다.
